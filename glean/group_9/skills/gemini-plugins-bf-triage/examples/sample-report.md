## Root cause hypothesis

- **Hypothesis:** Windows wall-clock resolution / Sleep-Win32 granularity on the failing host (`i-095998f34bdae8e10`, "Microsoft Windows Server (build 20348)") allows the parallel-shell `find` to legitimately reach `timesEntered: 3` on the `setPreYieldWait` failpoint with only 2 of its first 3 yield-time deltas exceeding the `overdueInterruptCheckIntervalMillis = 100ms` threshold — so the test's `assert.gte(overdueInterruptChecks, 2+1=3)` racy expectation is one short. The `assertDelinquentStats(... 2)` call on the line above passes because it asks for `>= 2`; only the `assertOverdueOpsSlowlogAndCurop(..., 2)` call (which internally asks for `>= count` overdue interrupts, with count=2 — but the prior commit history of the assertion show count is being misinterpreted as 2+1 elsewhere) trips. The fundamental issue is that the *server's* per-tick interrupt sampling rate on Windows is not deterministically 1-per-yield, so 3 forced delinquent yields do not always produce 3 overdue interrupt checks. SERVER-125404 (Jiaqi Tian, 2026-04-24, master commit `57d437d0`) tried to fix this by reducing `delinquentIntervalMs` from `waitPerIterationMs - 20` (180ms) to `waitPerIterationMs - 100` (100ms) so each 200ms-yield is well above the threshold, but BFG-3161130 fires on Windows master *after* that fix — proving the fix was insufficient.

- **Confidence:** `78/100` — three converging signals lock this in: (a) all 3 BFGs are Windows-only across two branches, with identical assertion; (b) the prior SERVER tickets `SERVER-125404` ("wall clock timer resolution drift could lead to test failure on windows", Closed/Fixed) and `SERVER-118528` ("fix undeterministic timing behaviour of failpoint") explicitly attributed earlier failures of the same assertion to Windows timing; (c) BF-42905 was closed/Fixed by SERVER-125404 and the issue has recurred — Liubov Molchanova's last comment ("The issue is similar to BF-42905 but still happening.") confirms this. Not 100 because we did not download the raw task log for forensic timeline analysis (Path A); some confidence is reserved against the chance the recurrence is a different bug with the same surface signature.

- **Supporting evidence:**
  - All 3 BFGs (`BFG-3161130`, `BFG-3130703`, `BFG-3095524`) report the same `actual=2, expected=3` for `overdueInterruptChecks`, on three different Windows variants (`bb_search_bfgs` results spooled to `/tmp/bf-triage-workdir-BF-43499/payloads/bb_search_bfgs_delinquent.json`).
  - `git_blame jstests/noPassthrough/delinquent_ops.js@2489e858` shows line 104 (`assert.gte(operationMetrics.delinquencyInfo.overdueInterruptChecks, count, ...)`) was introduced in commit `8ca11e5e` (SERVER-104009, Zixuan, 2025-08-26).

  - `mongodb-mongo-v8.3-staging` BFGs occurred at `3a6c91f8` (2026-04-29, *before* SERVER-125404 landed there — note that `git_log --grep=SERVER-125404` returns exactly one commit, on master only; never backported) and at `6d09d65f` (2026-05-14).
