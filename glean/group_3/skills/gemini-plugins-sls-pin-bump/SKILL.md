# SLS Pin Bump Shepherd

A weekly bot (`buildscripts/modules/atlas/bump_sls_pin.py`, private `sls-pin-bump`
Evergreen variant, cron Tuesdays 14:00 UTC on `mongodb-mongo-master`) bumps the
`pinned_sls_commit` in `buildscripts/modules/atlas/manifest.json` to the latest
green SLS commit on the `ds-services` waterfall. Each run cuts a fresh SERVER
ticket, opens or force-pushes a single PR on branch
`server-disagg-storage/bump-sls-pin`, and submits a DSC-only Evergreen
verification patch whose URL it comments on the PR.

This skill takes such a bump PR/ticket pair and shepherds it: make the simple
(green) case fast, and act as a structured guide for the hard (red) cases. Deep
fixes remain ordinary engineering; the skill gets you to a correct diagnosis and
strategy, not a magic fix.

Repo-specific recipes live in [references/operations.md](references/operations.md).
Failure classification lives in [references/failure-taxonomy.md](references/failure-taxonomy.md).

## Ground rules

- **Never push to the bot branch** `server-disagg-storage/bump-sls-pin`. It is
  force-pushed weekly; anything you push there is destroyed. All your work goes
  on a personal branch.
- **PRs you create are DRAFT only.** The operator flips draft to ready and
  merges. Never change a PR's draft/ready state yourself.
- **Jira ticket auto-creation is allowed.** If you created a ticket
  successfully, use the real key in the PR title (never a placeholder key).
- **Sign every agent-authored PR or Jira comment/description.** Final line of
  the body, plain ASCII, verbatim (including the backticks around the skill
  name):

  ```
  Generated by the `sls-pin-bump` skill, operated by @<operator-handle>.
  ```

  Derive the handle from the operator's gh/git identity (use the
  platform-appropriate mention on Jira). Each outward post still requires
  operator authorization unless they granted it for the session.
- **Copybara privacy:** never move content from copybara-excluded paths
  (`buildscripts/modules/**`, `src/mongo/db/modules/**`) into paths that sync to
  the public mongodb/mongo repo. When in doubt check
  `buildscripts/copybara/copybara_path_rules.json`.
- **Degraded-mode fallback:** when a mutating or authed action is blocked
  (permissions, expired auth, missing CLI), do not silently pivot. Present the
  exact command or content to the operator and let them execute it. The
  workflow must remain functional with the human acting as the auth wrapper.
- **Checkpoint** after every significant state change (see Checkpointing).

## Phase 1: Orient

1. From the given PR or ticket, find its pair (the PR body/title carries the
   ticket key; the ticket links the PR).
2. Confirm it is bot-generated: branch `server-disagg-storage/bump-sls-pin`,
   title `SERVER-NNNNN Import sls-proto: <hash>`, a verification-patch comment.
3. Extract the old and new pin from the `manifest.json` diff and note the SLS
   commit range `old..new` in 10gen/sls (source for changelog context when
   triaging).
4. **Check for competing bump PRs**: search open PRs touching
   `buildscripts/modules/atlas/manifest.json`. If another pin bump is in
   flight, coordinate or supersede explicitly; never race a duplicate bump.
5. Sanity-check the bot itself ran the expected script version (recipe in
   [references/operations.md](references/operations.md)).

## Phase 2: Audit the bump commit

The bump commit's diff must contain ONLY the import allowlist: `manifest.json`,
the two `flags-state.json` copies, and SLS proto files. Anything else is
contamination (it has happened; hardening exists but keep this as defense in
depth). On contamination: stop, report to the operator, do not recommend merge.

## Phase 3: Triage the verification patch

The bot's PR comment links a DSC-only patch (variant
`enterprise-amazon-linux2023-arm64-all-feature-flags-extra-system-deps`, task
tag `.assigned_to_jira_team_server_disagg`). Wait for it to finish, then
classify EVERY failure using
[references/failure-taxonomy.md](references/failure-taxonomy.md) before
declaring the pin good or bad.

Verify "known flake" claims live: check whether the same test fails on recent
mainline runs at the old pin. Never trust a hardcoded flake list.

## Phase 4: Green path

When all failures classify as pre-existing flakes/infra noise (or there are
none): post a signed evidence summary on the PR and recommend merge. Include
the pin range, the patch link, and a per-failure classification with evidence
links. Reviewers do read this comment; write it for them. The human merges.

## Phase 5: Red path

When real pin-caused failures exist, work this ordered decision procedure:

1. **Classify everything first** (Phase 3). If only flakes remain after real
   issues are explained, restart the flaky tasks for a clean run.
2. **Variant A (preferred): independent, old-pin-safe fix.** Gate: would the
   fix break CI while master is still on the OLD pin (does the old SLS binary
   tolerate it)? Evidence method: run a DSC patch of the fix applied WITHOUT
   the pin bump (recipe in operations reference). If old-pin-safe: cut a fix
   ticket, open a DRAFT fix PR, land it, and the untouched bot PR goes green
   and merges as-is. Keeps the bump revertable by ticket for release managers.
3. **Variant B: bundle.** When the fix and the bump cannot land separately
   (new-pin-only harness change), build a fresh personal branch off master,
   cherry-pick the bot's bump commit, add the fix, and open a DRAFT PR under a
   fresh ticket that supersedes the bot PR (one squashed commit on merge).
   Close the bot PR with a signed explanatory comment linking the successor.
4. **SLS-side blocker:** if the root cause is in the SLS binaries (no harness
   or config lever), escalate to the SLS team with a concrete question that
   states the observed mechanism and asks for the intended behavior. Do not
   chase config placebos; see the cautionary tale in the taxonomy reference.

## Phase 6: Post-merge and bot-ops

- A merged bump can still break the disagg variant later. The
  ticket-per-bump design exists so release managers can revert cleanly by
  ticket; hand post-merge breakage to BF triage with that context.
- Bot operational issues (orphan tickets with no PR, push permission failures,
  stale script version, ECR image rot on the old pin) are covered in
  [references/operations.md](references/operations.md). A glass-break merge
  under ECR rot is a human decision: document the option, never execute it.

## Checkpointing

Sessions churn; the shepherding state must survive. Maintain a checkpoint file
at `~/Documents/Tickets/<bump-ticket>/checkpoint.md` (template in the
operations reference) recording phase, pin range, evidence links, patch IDs,
and the next action. Update it on every phase transition, patch submission, or
significant finding. When authorized, mirror the checkpoint as a Jira comment
on the bump ticket so other operators (and future sessions) can resume. On
skill start, look for an existing checkpoint and resume from it.
