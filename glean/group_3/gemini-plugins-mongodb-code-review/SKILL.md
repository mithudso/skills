# MongoDB Code Review Workflow

## Prerequisites

- **`gh` (GitHub CLI):** must be installed and authenticated with `10gen/mongo` read access. The Setup phase and all of Phase 5 use `gh api` and `gh pr` commands.
- **Glean MCP server** (`mcp__glean_default`): used by the `alt-approaches` and `design-alignment` sub-agents to search Jira, Confluence, Slack, and Google Docs for ticket context. The other 12 sub-agents work without it. If Glean is unavailable, those two agents will produce shallower findings (diff-only, no ticket research).

## Setup: Fetch the PR

```bash
# Get title, body, changed files
gh pr view <number> --repo 10gen/mongo --json title,body,files,commits

# Get the full diff
gh pr diff <number> --repo 10gen/mongo

# Get existing review comments (avoid duplicating prior feedback)
gh api repos/10gen/mongo/pulls/<number>/comments \
  --jq '.[] | {path: .path, line: .original_line, body: .body, user: .user.login}'

# Check CI status
gh pr checks <number> --repo 10gen/mongo
```

## Comment Attribution & Style Guide Links

Every review comment generated by this skill MUST be prefixed with `**[mongodb-code-review · <sub-agent>]**`, where `<sub-agent>` is the `Tag` from the index above. When multiple sub-agents flagged the same issue after deduplication, list all of them: `**[mongodb-code-review · architecture, security]**`. The prefix tells authors which reviewer perspective generated the comment and signals that it is AI-generated.

When a comment concerns coding style, include a link to the relevant style guide:

| Topic                     | Link                                                                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| General C++ style         | [Server C++ Style Guide](https://github.com/mongodb/mongo/blob/master/docs/cpp_style.md)                              |
| Query-team-specific rules | [Query Team Style Guidelines](https://docs.google.com/document/d/1nBq0ZLHJTqSwsFqqxWqQRYH4OFVG-5ZzP-QB-_PDu_w)        |
| Code comment conventions  | [Query Team Code Comment Guidelines](https://docs.google.com/document/d/1YPGwQfugv9tkK6I8jL9FCbPesJIOQjccHtrvPsSCJDM) |
| Includes, license, basics | [Server Code Style Wiki](https://github.com/mongodb/mongo/wiki/Server-Code-Style)                                     |

Example:

```
**[mongodb-code-review · style-review]** [style] file.cpp:42 — Constants should use `k` prefix, not `UPPER_SNAKE`.
See [Query Team Style Guidelines](https://docs.google.com/document/d/1nBq0ZLHJTqSwsFqqxWqQRYH4OFVG-5ZzP-QB-_PDu_w).
```

Example (multiple sub-agents flagged the same issue):

```
**[mongodb-code-review · architecture, defensive-code]** [non-blocking] query_planner.cpp:210 — Precondition that `pipeline` is non-empty is assumed but not checked. Could we add a `tassert` here?
```

## Phase 1 — Parallel Sub-Agent Review

After fetching the diff and existing comments, launch **all fourteen sub-agents in parallel** using the Agent tool. Read the prompt file linked in the index above for each sub-agent and pass that prompt — verbatim — as the agent's instructions, along with the relevant slice of the diff (some sub-agents want the full diff; others want only C++/JS/Python files; the prompt file says which).

Each sub-agent returns findings in this format:

```
**[mongodb-code-review · <sub-agent-tag>]** [LABEL] file.cpp:42 — <one-line description>
<optional 1–2 sentence elaboration>
<If style-related, include a link to the relevant style guide from the table above.>
```

`<sub-agent-tag>` is the `Tag` column from the index. `[LABEL]` is one of: `BLOCKING`, `NON-BLOCKING`, `STYLE`, `OPTIONAL`, `FOLLOW-UP`, `SECURITY`.

---

## Phase 2 — Merge, Deduplicate, and Prioritize

After all fourteen sub-agents return:

1. **Deduplicate**: Collapse findings pointing to the same file+line or the same logical issue. Keep the most specific description. When multiple sub-agents flagged the same issue, list all their tags in the comment prefix (e.g. `**[mongodb-code-review · architecture, defensive-code]**`) — convergence from independent reviewers is a signal to upgrade severity.

2. **Consolidate by label priority:**
   - `SECURITY` — always surfaced first, always blocking unless clearly speculative
   - `BLOCKING` — must be resolved before merge
   - `NON-BLOCKING` — should fix but won't hold the PR
   - `STYLE` — must fix per Query Team style rules (see `references/query-team-style.md`)
   - `FOLLOW-UP` — file or offer to file a ticket; don't block
   - `OPTIONAL` — explicitly fine to skip

3. **Prune noise**: Drop findings that are pre-existing (not in the diff), that a compiler/linter would catch, or that are genuinely speculative without concrete evidence.

## Phase 3 — Comment Style & Calibration Labels

Tag every comment so the author knows what's a blocker:

| Label            | Meaning                                               |
| ---------------- | ----------------------------------------------------- |
| `[security]`     | Security concern — always surfaced first; blocking unless clearly speculative |
| _(unlabeled)_    | Blocking — must be addressed before merge             |
| `[non-blocking]` | Should fix but won't hold the PR                      |
| `[optional]`     | Nice-to-have, explicitly fine to skip                 |
| `[style]`        | Must be fixed                                         |
| `[follow-up]`    | Author should consider filing a ticket; don't fix now |
| `suggestion:`    | Concrete replacement — use a GitHub suggestion block  |

**Default to blocking for design questions.** Use `[follow-up]` when the code is correct but extensibility would require significant rework.

**Comment style:**

- Ask, don't direct. "Could we use `std::variant` here?" not "Use `std::variant`."
- Offer an alternative. A question without a suggestion puts all the work on the author.
- One thread per concern.
- Reserve "why?" for genuine questions — prefer "suggestion:" or "could we...?" for rhetorical critique.
- Use GitHub suggestion blocks whenever you have a concrete replacement.
- **AI label:** Append `[generated by \`mongodb-code-review\` skill]` on its own line at the end of every comment body — both inline threads and PR-level comments.

## Phase 4 — Output Summary to User

If the user passed `--post-as-pending`, skip this phase entirely and proceed directly to Phase 5.

Otherwise, output the full review to the conversation so the user can read it in context. Structure:

1. **Overall verdict** (one sentence): "Mostly clean — a couple blocking questions on the approach, some style nits" or "LGTM, minor suggestions only."
2. **Blocking items** (if any): numbered list, each with file:line, sub-agent tag, and the comment body.
3. **Non-blocking / style / follow-up items**: grouped by file, each with sub-agent tag and comment body.
4. **Things that looked good**: 1–2 genuine positives.
5. **Suggested review event**: `APPROVE`, `REQUEST_CHANGES`, or `COMMENT` — with rationale.

This summary is redundant with the inline comments staged in Phase 5, and that's intentional — the user gets a quick overview here and can fine-tune the inline comments on GitHub before publishing.

After presenting the summary, ask the user whether to proceed to GitHub staging:

> "Stage these as a pending GitHub review? (You can edit or discard before publishing.)
> Tip: pass `--post-as-pending` next time to skip this confirmation and go straight to staging."

If the user declines, stop here — the summary in the conversation is the deliverable.

## Phase 5 — Stage Pending GitHub Review

**CRITICAL: Do NOT publish the review.** All comments MUST be staged as a **pending** review so the user can inspect, edit, and publish them. The user is the reviewer of record — this skill drafts on their behalf.

### Step 1 — Create the pending review with all inline comments

Build a JSON file with the review body and all inline comments, then submit as a single pending review:

```bash
# Build the review payload — write to a file to avoid shell escaping issues
# with special characters (em-dashes, angle brackets, backticks, etc.)
cat > /tmp/review_payload.json <<'REVIEW_EOF'
{
  "body": "<PR-level summary — frame the review and sign-off in one comment>",
  "comments": [
    {
      "path": "src/mongo/db/query/planner.cpp",
      "line": 42,
      "side": "RIGHT",
      "body": "**[mongodb-code-review · architecture]** [non-blocking] ..."
    },
    {
      "path": "src/mongo/db/query/planner.cpp",
      "line": 108,
      "side": "RIGHT",
      "body": "**[mongodb-code-review · defensive-code]** [follow-up] ..."
    }
  ]
}
REVIEW_EOF

# Submit as pending — this does NOT notify anyone
gh api repos/10gen/mongo/pulls/<number>/reviews \
  --method POST \
  --input /tmp/review_payload.json
```

See `references/github-pending-review.md` for the full API quirks reference (no `event` field, non-empty body requirement, `side: RIGHT`, file-based payload, `line` vs `position`). Omitting the `event` field ensures nothing is visible until the user explicitly publishes.

### Step 2 — PR-level review body

The `"body"` field of the review serves as both the opening comment and the sign-off. Keep it short:

- **Frame the review:** "A couple of comments below — mostly questions, nothing blocking" vs. "Holding off on approval until we resolve X."
- **Right approach?** If there's a fundamentally different design worth discussing, say so here.
- **Scope / split?** If this should be multiple PRs, say so.
- **Missing pieces?** Call out absent components (migration path, rollback, config flag, docs).
- **Call out one or two things you genuinely liked.** "Lots of deleted code." / "The new splitPipeline stuff is much cleaner."
- **Summarize your blocking asks** (if any) in one sentence.

### Step 3 — Verify the review is PENDING (self-check before reporting)

Before telling the user anything, confirm the review was staged correctly:

```bash
# Fetch the review that was just created (the ID is in the POST response)
gh api repos/10gen/mongo/pulls/<number>/reviews/<review_id> \
  --jq '{state: .state, body_chars: (.body | length), submitted_at: .submitted_at}'
```

Expected: `"state": "PENDING"`. If the state is anything else (`APPROVED`, `CHANGES_REQUESTED`, `COMMENTED`), the review was published immediately — **stop and tell the user** before proceeding.

Also confirm inline comments were attached:

```bash
gh api repos/10gen/mongo/pulls/<number>/reviews/<review_id>/comments \
  --jq 'length'
```

If the count is 0 but comments were expected, the inline payload was malformed — report the discrepancy to the user rather than claiming the review is ready.

Only proceed to Step 4 after both checks pass.

---

### Step 4 — Tell the user what to do next

After staging, tell the user:

> Pending review staged with N inline comments. To review and publish:
>
> 1. Open the PR: `https://github.com/10gen/mongo/pull/<PR_NUMBER>` (substitute the PR number)
> 2. Click the green "Review changes" button — your pending comments will appear
> 3. Edit any comments you want to adjust
> 4. Choose Approve / Request Changes / Comment and submit
>
> Or to discard: click "Discard review" in the same menu.

**Never submit with `APPROVE`, `REQUEST_CHANGES`, or `COMMENT` event directly.** Always use `PENDING`. The user decides the final event when they publish.

## Follow-up Ticket Pattern

Rather than blocking on a hard design question:

1. Leave a `[follow-up]` comment explaining the concern
2. Offer to file the ticket (or file it yourself and drop the number in the comment)
3. Approve the PR

Right call when: the code is correct, concern is about future extensibility, fix would require significant rework.

## Quick Anti-pattern Reference

| Mistake                                                      | Fix                                                             |
| ------------------------------------------------------------ | --------------------------------------------------------------- |
| Blocking on style when the code is correct                   | Use `[style]` or `[optional]`                                   |
| Design critique with no alternative offered                  | Always propose a concrete option                                |
| Reviewing only the diff                                      | Check related call sites (grep), adjacent files, and the ticket |
| Piling `[optional]` comments on one author                   | Pick the 2–3 that matter most                                   |
| "Why did you do X?" as rhetorical criticism                  | Say what you'd prefer or what you expected instead              |
| Blocking on a design debate that could be a follow-up ticket | File the ticket, approve                                        |
