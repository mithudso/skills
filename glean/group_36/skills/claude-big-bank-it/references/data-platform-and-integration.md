## The data-platform estate: EDW → data lake → lakehouse

**The heritage layer is the enterprise data warehouse (EDW)** — built over 1–2 decades on proprietary appliance warehouses (**Teradata, Oracle Exadata, IBM DB2/Netezza**, mid-tier SQL Server), fed by nightly batch ETL. Scale is significant (KeyBank reported >30 PB in Teradata; NAB's 26-year-old platform supported "thousands of daily data feeds … 140+ reporting suites").[^1][^5] A typical bank also has "a Hadoop cluster on the side for data science, a constellation of reporting databases … a SAS estate."[^4] *(Confidence: fact / qualified.)*

**The data-lake era (Hadoop/HDFS) is now legacy and broadly judged a disappointment.** Banks layered Hadoop "data lakes" alongside the EDW ~2012–2015 for cheap storage + data science; a tier-1 institution ran a multi-petabyte Cloudera CDH/HDFS cluster (25+ component ecosystem: Hive, Spark, Oozie, Sqoop, Ranger, Kerberos, Atlas, Impala) now end-of-support and being migrated off.[^2] *(Confidence: fact; the disconfirming evidence on data-lake failure is strong — see below.)*

**The current convergence target is the lakehouse on cloud object storage with open table formats** — object storage (S3/ADLS/GCS) in open formats (Parquet + Delta Lake / Apache Iceberg / Hudi), decoupled elastic compute, warehouse-style ACID/governance on top. Named bank migrations: NAB → Databricks/Delta on AWS ("Ada," decommissioned Teradata end-2023); TD Bank → Azure Databricks/Delta; KeyBank → Google BigQuery; a tier-1 bank → Databricks with **Delta Lake + Iceberg interoperability**, replacing Hive Metastore/Atlas with Unity Catalog (55% cost reduction).[^1][^2][^5][^6] **Databricks (Delta Lake)** and **Snowflake (Iceberg/hybrid)** dominate; **Apache Iceberg as the open table format** is repeatedly cited as the property enabling lineage, time-travel, snapshot history, and engine portability — and as the structural answer to vendor lock-in.[^3][^4] A 2026 UK-FS reference architecture describes a medallion-style governed lakehouse that must "stand up in front of PRA/FCA," with frequent **EDW↔lakehouse coexistence.**[^3] *(Confidence: fact for the named migrations; qualified for the single-source reference architecture.)*

**Where document/operational stores fit (neutral):** the lakehouse is the *analytical* plane. Several sources position a document-model **Operational Data Layer (ODL)** as a distinct *operational* pattern — consolidating data from systems of record into a queryable layer to decouple modern apps from legacy cores, "not intended to replace pure analytics platforms."[^op3] This is the conceptual seam where MongoDB-style operational stores sit (vs. the lakehouse). *(Confidence: qualified — one vendor doc + generic dual-plane corroboration.)*

## Operational vs analytical split, data mesh, golden source

**The architecture converges on a dual-plane model:** OLTP "systems that own current state" (operational/transactional plane = the system of record) vs. OLAP "systems that answer analytical questions" (analytical plane), with **CDC or batch ETL/ELT replicating between them** — "default to running both; the cost of forcing either workload onto the other's database compounds."[^op1][^op4] A cautionary real-world note: NAB found it had been running *operational* payments/lending logic *inside* its Teradata analytical platform and repatriated those apps to the core "where they belonged."[^7] *(Confidence: fact.)*

**Data mesh** (Zhamak Dehghani, 2019: domain-oriented ownership, data-as-a-product, self-serve platform, federated computational governance) is among the most-cited *and most-disconfirmed* bank patterns. The central-data-team bottleneck is acute, but at banks "mesh cannot be a free-for-all" — federated governance must enforce classification/access/lineage/quality *at the point of publication*, driven by BCBS 239/MiFID II/SFDR.[^mesh3] The headline disconfirmation: only **~18% of organizations** have the governance maturity to run a mesh (traced to Gartner's 2021 Data & Analytics Governance Survey); Thoughtworks (which originated the hypothesis) confirms data mesh "is an organisational transformation, not a technical one."[^mesh1] *(Confidence: fact for the 18% maturity figure; the "82% stall" framing is one analyst's gloss.)*

**"Golden source" / single-source-of-truth and MDM** are foundational and **directly mandated by regulation**: BCBS 239 states "a bank should strive towards a single authoritative source for risk data per each type of risk."[^mdm1] MDM covers **master data** (customers, accounts, products) and **reference data** (codes, hierarchies). A persistent operational reality: because each system stores its own data, banks rely on **reconciliation reports** against accounting data as a routine control — reconciliation is "a necessary capability," not an embarrassment.[^mdm3] **BCBS 239** (RDARR; 2013, reinforced by the ECB's 2024 RDARR guide) drives the architecture by requiring a single authoritative source per risk type and attribute-level **data lineage** — flagged here as the *driver*; the regulation itself → `fsi-banking-regulatory-context`.[^mdm1][^mdm4] *(Confidence: fact.)*

## Streaming & real-time data: Kafka as the event backbone

**Apache Kafka is repeatedly described as the "de facto standard" event backbone at banks**, deployed as shared platform-engineering infrastructure (a central team owns cluster ops; many teams consume).[^kafka1] Named production use cases:
- **CDC off the core / mainframe offload** (the dominant "modernize without ripping out the core" move): RBC wrote a microservice on Confluent/Kafka to "significantly reduce the reads on the mainframe" (50+ apps on its event-driven architecture); a Thai bank (Krungsri) uses IBM CDC → Kafka as the intermediary between mainframe and consumers ("subscribe once, publish many"); Nationwide Building Society started with CDC into Kafka to take load off back-ends; Macquarie BFS implemented event-sourcing via CDC (AWS DMS/Debezium).[^rbc][^kafkafraud][^nationwide][^macquarie]
- **Payments:** Lloyds' New Payments Architecture went live Nov 2023 on event-driven processing; Mindgate (India) rebuilt payments on Confluent/Kafka for UPI at ~1B txns/day.[^lloyds][^mindgate]
- **Fraud/real-time analytics:** a Thai bank blocks fraudulent payments in <60s on Kafka/Confluent.[^kafkafraud]
- **Stream processing:** Kafka Streams/KSQL (Nationwide) and the broader Kafka + Flink/Spark Streaming pattern.[^nationwide] *(Confidence: fact — multiple independent cases.)*

**The move from nightly-batch ETL to streaming/CDC is the throughline;** Confluent's banking footprint is substantial (RBC, KeyBank, Lloyds, Nationwide, Krungsri, Mindgate), and banks frequently choose *commercial* Confluent over raw OSS Kafka for "enterprise-grade stability … lower operational risks."[^keybank][^mindgate] *(Confidence: fact / qualified — vendor case studies.)*

## Integration architecture: ESB/SOA → API-led + gateways

**The legacy layer is the ESB/SOA estate** — TIBCO BusinessWorks, IBM Integration Bus / WebSphere MQ / DataPower, Oracle Service Bus, webMethods — on-prem middleware that "owns the integration logic centrally," plus SOAP services. **IBM MQ remains the bank message-queue workhorse.**[^esb] The clean taxonomy (load-bearing for credibility): **ESB** (centralized on-prem orchestration) → **iPaaS** (cloud-native successor: MuleSoft Anypoint, Boomi, Workato) vs. **API gateway** (narrower: inbound traffic mgmt, auth, rate-limiting — Kong, Apigee, AWS API Gateway, Azure APIM) — "most large enterprises need both."[^esb] *(Confidence: fact.)*

**The shift is to API-led connectivity** — MuleSoft's three-tier model (System APIs unlock cores; Process APIs orchestrate; Experience APIs shape per-channel) is the canonical banking pattern, with accelerators abstracting cores like Temenos/AS400 into canonical REST APIs.[^muleapi] **Open-banking regulation (PSD2 / UK Open Banking) is the primary driver of bank API programs** (as a *driver*; the regulation → `fsi-banking-regulatory-context`): the architecture it forces is gateways doing mTLS termination with TPP certs, **FAPI** (Financial-grade API security profile on OAuth 2.0) enforcement, consent validation, and full audit logging — banks typically *buy* the FAPI-compliant authorization server (ForgeRock, Ping, Curity) rather than build it.[^retailapi][^apigee] The "API as a product" model and internal API marketplaces are explicit goals (e.g. ING's 2018 "Banking as a Service" — MuleSoft backbone + Kong gateway + Apigee analytics + Kafka, reported 250+ fintech partnerships, 83% API reuse, integration costs down 65%; single-source figures — qualified).[^ing] *(Confidence: fact / qualified.)*

## Build-vs-buy and large in-house engineering

**Big banks employ tens of thousands of engineers and increasingly frame themselves as technology companies. Attribute and date headcount/spend — figures vary by source/year:**
- **JPMorgan Chase:** 2026 recruiting copy cites "over 55,000 technologists / $15B tech spend"; 2026 leadership coverage cites "more than **65,000 technologists** and a ~**$18B (rising to $19.8B)** budget (~10% of revenue), with ~2,000 AI engineers." The **65k / ~$18–19.8B** numbers are the most recent (2026) — do not state a single canonical figure without the date.[^jpmjobs][^jpmcio][^jpmbi]
- **Capital One:** the clearest "technology company that does banking" case — stated goal since 2012; first US bank to fully **exit its data centers (all 8, by 2020) and go all-in on AWS**, rebuilding ~80% of apps cloud-native; ~11,000 (2020) → ~14,000 (2026) technologists, ~85% engineers.[^capone][^caponeaws]
- Sector-wide: bank AI talent grew ~25% YoY across the 50 largest firms (Evident Insights, 2025), AI headcount approaching ~90,000.[^ciodive] *(Confidence: fact for the named banks; qualified for sector figures — single analyst source.)*

**The build-vs-buy calculus is genuinely contested** (see disconfirming). Pro-build logic: roadmap control, differentiation, avoiding lock-in, AI "sovereignty" (JPMorgan's proprietary LLM Suite rolled to ~200k employees). The honest reality is **hybrid** — "the majority of banking IT projects use elements of both build and buy"; the modern framing is "ditch the build-vs-buy mentality" for a platform/compose approach.[^builddev] **Open-source adoption is institutionalized via FINOS** (Fintech Open Source Foundation; founded 2018, joined the **Linux Foundation 2020**, **surpassed 100 members in January 2025**) — Platinum members include Citi, Goldman Sachs, JPMorgan, Morgan Stanley, RBC, plus all three hyperscalers; banks both contribute (JPMorgan's Perspective, Goldman's Alloy, the FDC3 interop standard) and consume (**JPMorgan was the first major US bank to use FINOS's Common Domain Model / ISDA DRR as a primary regulatory-reporting mechanism**, 2024). The driver: cloud migration + an influx of Silicon-Valley-trained engineers normalized open source in "a notoriously cautious, heavily regulated industry," and banks use OSS contribution to *attract talent*.[^finos][^finosjpm][^finosciodive] *(Confidence: fact.)*

## Disconfirming evidence

1. **Data lakes/Hadoop largely failed on their own terms.** Gartner estimated **60–85% of big-data projects failed**; the "data swamp" was predicted (Stonebraker) and realized 2015–2018. An arXiv 15-year review finds root causes are "organizational far more than technical" ("governance debt") — and pointedly that lakehouse and data mesh advanced the *technology* but "the organizational record barely moved." Each wave repeated the same governance mistake.[^neg1][^neg2]
2. **Data mesh at banks is mostly aspirational** — only ~18% have the governance maturity; the "mesh" is frequently a warehouse with new branding (source-system teams rebadged as "domains," no funded data-product-manager role). Regulated FS is the *strongest* case for mesh yet the *hardest* to execute, because the center must cede control before domains prove they can hold it.[^mesh1][^negmesh1]
3. **Kafka is frequently overkill — even Confluent says so.** It needs ~0.5–3 FTE to operate and is wrong for low-volume (<~10k msg/day), request-reply/synchronous, sub-ms HFT, bad networks, and tens-of-thousands of client endpoints. It's the *de facto choice when its specific properties (multi-consumer fan-out, replay, sustained high throughput, immutable audit log) are genuinely needed* — and a liability otherwise.[^negkafka1][^negkafka3]
4. **Build (in-house) often costs more and fails more than the pro-build narrative admits.** Forrester (via DevOps.com): in-house builds have higher TCO 64% of the time and blow budgets 88% of the time; common failure mode is "key architect leaves mid-program" and codebases "drift toward unmaintainable complexity within 3–5 years." Conversely, *buying* also fails (e.g. a regional bank's A$5M Temenos write-off) — so the honest framing is **hybrid/platform, not build-vs-buy as a binary.**[^negbuild1][^negbuild2]
5. **Open banking (the API-program driver) has badly underdelivered.** Germany: only **~8.7% of payment accounts** accessed via TPP APIs; eight years in, "we are not getting closer to interoperability" (80+ fragmented frameworks) — because banks had **no commercial incentive** to build high-quality APIs, so they shipped compliant-but-unusable ones ("API sprawl"). *Counter-evidence:* UK hit ~16M users by late 2025 (real scale, but mostly invisible "behind the scenes"). So a bank's API programs are often **compliance-driven and minimally performant** — important nuance when assessing real API maturity.[^negob1][^negob3]
6. **Headcount/spend figures are inconsistent and must be dated** — JPMorgan appears as both "55,000 / $15B" (recruiting copy) and "65,000+ / $18–19.8B" (leadership coverage), both 2026.[^jpmjobs][^jpmcio]

## Seller takeaways

- **The data/engagement layer around the core is the real opportunity** (see `core-banking-and-sor-soe.md`); within it, distinguish the **analytical plane** (lakehouse — usually not the operational fit) from the **operational plane** (where document/operational stores and an ODL sit).
- **CDC off the core/mainframe is the dominant low-fear modernization motion** — "we sit beside the core via CDC/streaming and serve real-time apps" aligns with how banks actually modernize.
- **Assess real API/data maturity skeptically** — "we have open-banking APIs" or "we run a data mesh" often means compliance-grade, not production-grade. Calibrated questions about governance, reconciliation, and who owns data products land as credibility.
- **Respect build-heavy culture without over-indexing on it** — big banks build a lot, but in-house build fails often; the credible posture is "compose," not "build vs buy." FINOS familiarity signals you understand their open-source posture.
