# Reference: Step 9c — Write-tool truncation fallback (stub-then-append)

> Read this file only when the primary `Write` of the report has
> failed with a JSON-marshalling / truncation error. The main
> `SKILL.md` Step 9c section points here.

When the agent's `Write` tool call fails with a JSON-marshalling error
(`Expected ',' or '}' after property value in JSON at position N`,
`Unexpected end of JSON input`, or any error that indicates the
`contents` arg block was truncated on the way out — see Step 5.0 for
the root cause), the agent **MUST** automatically switch to the
stub-then-append pattern instead of retrying the same `Write` with the
same payload. The retry-as-is is guaranteed to fail again because the
payload size is the root cause.

This fallback uses the runtime's **anchor-replace tool** for the
per-section appends. Different agent runtimes name this tool
differently:

- **Cursor**: `StrReplace` (with `old_string` / `new_string` /
  optional `replace_all` parameters).
- **Claude Code**: `Edit` (with `old_string` / `new_string` /
  optional `replace_all` parameters — same shape, different name).

In the rest of this section, **`EditAnchor`** is a placeholder for
whichever tool the current runtime exposes. Substitute the local
name when actually calling the tool.

## Trigger conditions

Any of these on the same target path:

1. First `Write` of the full report returns a JSON-marshalling error.
2. Second `Write` of the same payload returns the same class of error.
3. A `Shell` heredoc fallback with the same payload returns
   `Unexpected end of JSON input` on its args block (same root cause —
   the heredoc body lives inside the `command` arg).

## Recovery procedure

1. Write a **small skeleton** (≤ 1 KB) with `Write`:

   ```markdown
   # Triage Report — `<BF-KEY>`

   > Generated by the `bf-triage` skill.
   > Generated at: `<UTC timestamp>`.
   > Note: this report was assembled via the Step 9c stub-then-append
   > fallback path because the initial `Write` of the full payload
   > exceeded the tool-call serialization budget. Content is unchanged.

   <!-- SECTIONS_BELOW -->
   ```

   The `<!-- SECTIONS_BELOW -->` HTML comment is the unique anchor
   the per-section `EditAnchor` calls will replace.

2. For each section listed in `templates/report_template.md`
   (`Header`, `Failure summary`, `Severity classification`, ...,
   `Appendix`), call `EditAnchor` once with:

   - `old_string = "<!-- SECTIONS_BELOW -->"`
   - `new_string = "<rendered section markdown>\n\n<!-- SECTIONS_BELOW -->"`

   The anchor migrates to the bottom after each call. Each
   `EditAnchor` payload contains only one section, which keeps every
   individual tool-call args block well under the truncation
   threshold (typical section: 1-5 KB).

3. After the final section (`Appendix`), do one last `EditAnchor` to
   remove the anchor:

   - `old_string = "\n\n<!-- SECTIONS_BELOW -->"`
   - `new_string = ""`

4. Verify the file: `wc -l "$MD_OUT"` should match the agent's expected
   line count within ~5 lines (small drift from trailing newlines).

## Recording the fallback in the report

- The skeleton's `Note: ...` banner stays in the final report header so
  the human reviewer knows the assembly path was different. Do NOT
  remove it.
- Add one bullet to the report's `Appendix` § "Tool failures
  encountered": `Write tool truncated on first attempt (<error
  message>); used Step 9c stub-then-append fallback to assemble the
  report from <N> sections via the runtime's anchor-replace tool.`

## When NOT to enter this branch

- Any non-truncation `Write` failure — permission denied, parent dir
  missing, disk full, etc. Those are real errors and the agent should
  surface them to the user, not paper over with the stub-then-append
  trick.
- Mode B subagents writing per-BF reports — they almost never hit the
  threshold because each subagent has a fresh context (see Step 0.5
  fan-out rule). If a subagent does hit it, the same fallback works
  inside the subagent.
- Mode C triager / grader subagents — same as above.

This fallback is also referenced by the Step 5.0 context-hygiene
rule as the "second line of defence" — Step 5.0 prevents the
truncation in most runs, Step 9c handles the residual cases where it
slips through anyway.
