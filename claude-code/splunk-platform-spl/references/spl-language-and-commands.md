## The search pipeline model
A search is a chain of commands separated by the pipe `|`. The first token after each pipe is the command name; the rest is its arguments.[^1] The pipe "tells Splunk to use the output of one command (left of the pipe) as the input for the next (right of the pipe)," refining data at each step.[^1] Events flow **left-to-right**: search terms (keywords, phrases, Booleans, key/value pairs) retrieve events from the index(es), then commands filter, extract, evaluate, calculate, or chart them.[^1]

The leading `search` command is **implied** — you don't type `search` for the first terms.[^2] `search` can also appear later to filter prior results. Behaviorally: as the *first* command it is **generating**; later in the pipeline it is **distributable streaming**.[^2][^6] Transforming commands like `stats`/`chart` do **not** pass `_raw` downstream, so a later `search` must use explicit field-value pairs.[^2]

## Command types (and why they matter for performance)
Splunk classifies almost all commands into **six types** (not mutually exclusive): distributable streaming, centralized streaming, transforming, generating, orchestrating, dataset processing.[^4][^6]
- **Distributable streaming** — per-event, one-in/one-or-zero-out, **order-independent**, so it can run on the **indexers** in parallel (map phase) — *but only if every preceding command can also run on the indexer; once processing moves to the search head it cannot move back*. Examples: `eval`, `rex`, `rename`, `fields`, `where`, `lookup` (default `local=false`), and later-pipeline `search`.[^4][^6][^2]
- **Centralized (stateful) streaming** — per-event but **order matters**, so it runs **only on the search head**; no indexer parallelism. Examples: `head`, `streamstats`, `transaction`, some `dedup`/`cluster` modes.[^4][^6]
- **Transforming** — orders results into a table, turning event values into numeric/statistical results for visualizations; **non-streaming**, outputs **results, not events** (you can't run an event-expecting command after one). Examples: `stats`, `chart`, `timechart`, `top`, `rare`, `addtotals`.[^4][^6]
- **Generating** — returns/generates results and **takes no pipeline input**; invoked with a leading pipe (`| tstats …`, `| makeresults`). The implicit `search` is the exception. Examples: `tstats`, `makeresults`, `inputlookup`, `metadata`, `rest`, `mstats`.[^4][^6] (Gotcha: a comment placed *before* a generating command makes the search fail.)[^6]
- **Orchestrating** — controls *how* a search runs without changing the result set. Examples: `redistribute`, `noop`, `localop`, `lookup` with `local=true`.[^4][^6]
- **Dataset processing** — needs the **entire dataset** to run. Examples: `sort`, `eventstats`, and some `dedup`/`fillnull`/`join` modes.[^4][^6]

**Why it matters (map-reduce):** the SH sends the query to the indexers, which process local data in parallel and return partial results (map), then the SH combines them (reduce).[^5] As long as commands are distributable streaming, work stays distributed. The moment a **non-streaming** command appears, all events must gather at the SH, and **once processing moves to the SH it never returns to the indexers** — every subsequent command runs single-threaded on the SH.[^6][^4][^5] Best practice: **put distributable streaming commands as early as possible, non-streaming as late as possible.**[^6][^5] A subtlety: the *same* command can change type by invocation — `fillnull` is distributable streaming **with** a field-list but dataset-processing **without** one; `lookup` is streaming with `local=false` but orchestrating with `local=true`.[^4][^5]

## Core commands (purpose + example)
- **`search`** — retrieve events or filter prior results (implied first). `index=web status=200 action=purchase`.[^1][^2]
- **`stats`** — aggregate statistics (count, sum, avg, dc, values…) over the whole result set; with `BY`, one row per group (SQL-like). Transforming. `sourcetype=access_* | stats count BY status, host`.[^7][^6]
- **`stats` vs `eventstats` vs `streamstats`** — same functions, different output:[^8][^9][^10]
  - `stats` works on the result set **as a whole**, returns only aggregated fields (events gone).
  - `eventstats` computes the same aggregations but **adds them inline as new fields to every event** (events not transformed); a **dataset-processing** command.
  - `streamstats` computes a **running/cumulative** aggregation **at the time each event is seen** (e.g., running total); a **centralized streaming** command. `| makeresults count=4 | streamstats count`.
- **`eval`** — compute an expression (math, string, conditional, eval functions) into a new/existing field. Distributable streaming. `... | eval full_name = first." ".last`.[^6][^11]
- **`where`** — filter using a Boolean **eval-expression**; unquoted tokens are field names, so it can compare two fields (unlike `search`). Distributable streaming. `... | where distance/time > 100` or `... | where ipaddress=clientip`.[^12]
- **`rex`** — search-time extraction via **named regex capture groups**, or `mode=sed` for replace/anonymize. Distributable streaming. `... | rex field=_raw "From: (?<from>.*) To: (?<to>.*)"`; mask: `... | rex field=cc mode=sed "s/(\d{4}-){3}/XXXX-XXXX-XXXX-/g"`.[^13]
- **`lookup`** — enrich events by matching event fields to a lookup table (CSV, KV Store, or script) and outputting fields inline. Distributable streaming (`local=false`). `... | lookup dnslookup clienthost AS host OUTPUT clientip`.[^14]
- **`inputlookup`** — read a lookup table as the *source* of a search; a generating command, leading pipe. `| inputlookup customers.csv` (pair with `outputlookup` to write back).[^15]
- **`join`** — combine left (main) and right (subsearch) datasets on shared field(s), SQL-style (`inner`, `outer`/`left`). **Discouraged** (see below). `... | join product_id [search vendors]`.[^17]
- **`transaction`** — group events into one transaction by shared field values + optional `maxspan`/`maxpause`/`startswith`/`endswith`/`maxevents`; retains raw text, computes `duration`/`eventcount`. Centralized streaming; resource-heavy (see below).[^18]
- **`tstats`** — high-performance statistics over **indexed fields in tsidx** / accelerated data models. Generating. `| tstats count WHERE index=web BY host`.[^21] (See below.)
- **`timechart`** — transforming aggregation with **`_time` always the x-axis**; optional split-by field → one series per value. `index=_internal | timechart avg(eps) by processor`.[^timechart]
- **`chart`** — transforming aggregation with an **arbitrary** x-axis (`over`), optional `by`; use when you need a non-time x-axis. `... | chart sum(bytes) over clientip by host`.[^chart]
- **`top` / `rare`** — most/least common values of a field (default limit 10); transforming. `... | top limit=100 dst_port`.[^toprare]
- **`dedup`** — remove events with duplicate field-value combos (keep N; `sortby` controls which). Streaming, or dataset-processing with `sortby`. `... | dedup host`.[^dedup][^4]
- **`sort`** — order by fields (`-` desc, `+` asc). A **dataset-processing** command (forces work to the SH). `... | sort - count`.[^6]
- **`fields`** / **`table`** — keep/remove fields (`fields`, distributable streaming) / render fields as a table (`table`). `... | fields host clientip`.[^cmdref]
- **`rename`** — rename fields (wildcards ok; quote names with spaces). Cannot merge fields — use `eval`+`coalesce()`. `... | rename pid AS product_id`.[^rename]
- **`fillnull`** — replace nulls (default `0`). Streaming with a field-list; dataset-processing without. `... | fillnull value=NULL status`.[^fillnull][^4]
- **`makeresults`** — generate N in-memory results (only `_time` unless `annotate=true`); report-generating, leading pipe, not indexed. `| makeresults count=4`.[^makeresults]

## `tstats` and accelerated data models
`tstats` runs statistical queries on **indexed fields stored in `.tsidx` files** — index-time fields or **accelerated data model** summaries.[^21] Because it searches index-time fields instead of scanning raw events, it is **much faster than `stats`**.[^21] You query an accelerated model via `tstats ... FROM datamodel=<model>.<root>`.[^21] A **data model acceleration summary** is a "high-performance analytics store" of `.tsidx` files holding indexed `field::value` combos plus their locations, optimized to accelerate searches over the model's fields.[^22] If a `tstats` search's range extends past the summary's range, it returns summarized results for the covered window and falls back to slower raw data for the rest (partial acceleration); `summariesonly=true` restricts results to the summary only.[^22] The `PREFIX()` directive lets `tstats` treat a raw indexed segment as a field, running over the tsidx and cutting indexer CPU.[^21] **Disconfirming:** a **high-cardinality field in the `WHERE` clause** can make `tstats` *slower* than a regular search (it must evaluate many distinct tsidx values); `tstats` is also weak at returning very many rows.[^21]

## The Common Information Model (CIM)
The **CIM is a shared semantic model**, delivered as an **add-on** containing pre-configured **data models, documentation, and tools** for consistent, normalized treatment of data at search time.[^cim] Each data model defines **normalized field names and event tags** for a domain. The CIM acts as a **search-time schema** ("schema-on-the-fly"): you map fields from disparate sourcetypes to common names via field aliases, extractions, and lookups, **leaving raw data intact**.[^cim][^cimnorm] Once normalized, you can build reports, **correlation searches**, and dashboards across vendors — and your data populates apps that require CIM compliance, notably **Splunk Enterprise Security** and the PCI app, which display only CIM-conformant data.[^cim] CIM data models can be **accelerated** so ES searches run via `tstats` over the summaries — tying CIM directly to the tstats/acceleration story.[^esdm][^cimfields]

## Subsearches
A **subsearch** is a search within a primary search, enclosed in **square brackets `[ ... ]`**, and it **runs first**.[^sub] Its purpose: return a single dynamic piece of information injected as a criterion into the main search.[^sub] The first command inside must be a **generating command** (`search`, `inputlookup`, `tstats`, etc.; `foreach` is the exception).[^sub] Nested subsearches run **innermost first**.[^sub] Example: `sourcetype=syslog [search sourcetype=syslog earliest=-1h | top limit=1 host | fields + host]` — the bracketed search finds the top host and its result becomes a filter.[^sub]

**Return/format:** subsearch results expand into the outer search as a search expression. The `return` command passes values up — by default the first row; multiple values are OR'd, e.g. `return 2 user ip` → `(user=bob ip=...) OR (user=fred ip=...)`.[^return] Cap output inline with `| format maxresults=<n>`.[^sub]

**Limits (why they don't scale):** a subsearch returns a **max of 10,000 results** and runs for a **max of 60 seconds**; over 60s its results are **automatically finalized (silently truncated)**.[^sub][^subtut] `join`/`append`/`appendcols` use a separate cap — `subsearch_maxout` in `limits.conf`, default **50,000**.[^17][^sub] Subsearches "rely on additional trips to the indexers, which increases overhead" and in large environments "will timeout before [they] complete" — so the documented guidance is to **rewrite to limit events, use lookups, or use `stats` instead**, and to pre-compute frequently-run large results into a lookup via `outputlookup`.[^sub] Splunk: "It is often possible to rewrite the search and omit the subsearch."[^sub]

## Why `join` and `transaction` are discouraged
**`join`:** the reference says use it "when the results of the subsearch are relatively small, for example 50,000 rows or less," and caps the right side at **50,000 rows / 60 seconds** "to limit the impact … on performance and resource consumption."[^17] It ships an explicit **"Alternative commands"** section recommending `stats`, `append`, `lookup`, `transaction`, or plain `search`+`stats`.[^17] In a distributed search, `stats` performs better because `join` is centralized on the SH; the common pattern is to replace `join`/`append` with a single base search over both datasets plus **`stats … BY <key>`** (using `values()`/`latest()`), keeping it one trip to the indexers.[^subperf][^joincomm] Hitting the 50k/60s caps **silently truncates** results, which often goes unnoticed and yields incorrect answers.

**`transaction`:** a **centralized streaming** command — all work happens on the SH (the indexers are "merely fileservers"), there is **no map-reduce**, and "nothing can be discarded along the way," causing an "explosion of RAM consumption on the search head."[^txnlarge][^4] When it exhausts memory it **drops further work and returns what it has with no indication the result is incomplete** (silent truncation).[^txnmaxspan][^txnlarge] Remedy: "you can almost always use `stats` instead" — typically `stats min(_time) max(_time) ... BY <id>` to compute duration.[^txnvsstats][^txnlarge] `transaction` is justified mainly when a unique ID alone is insufficient (recycled IDs needing time/pause segmentation), when grouping by start/end markers, or when you must preserve raw events.[^txnvsstats][^17]

## SPL2 — VOLATILE
SPL2 (Search Processing Language version 2) is Splunk's **next-generation search and data-preparation language**. As of the **January 16, 2026** GA, it reached worldwide availability in Splunk Enterprise and Splunk Cloud Platform and is positioned as "the single language powering the Cisco Data Fabric."[^spl2blog] It is used across **Edge Processor**, **Ingest Processor**, and the SPL2 Search and Reporting app.[^spl2blog][^whyspl2]

High-level differences from SPL1:[^whyspl2][^spl2blog]
- **Statement/pipeline-based and modular:** an SPL2 **pipeline** specifies which data to process, how, and where to send results; a multi-statement **"module"** chains statements and defines reusable **custom functions** and **custom data types** (with type checking — unlike macros).
- **SQL-like + SPL-like hybrid:** supports SQL `FROM`/`WHERE`/`GROUP BY`/`ORDER BY`/`JOIN` clauses alongside SPL.
- **Unified across data-in-motion and data-at-rest:** the same SPL2 logic transforms streaming data (Edge/Ingest Processor) and data at rest (search) — "learn once, use everywhere."
- **New capabilities:** RBAC-enforced **data views** over indexes, conditional in-stream data dropping, and modern JSON handling with **lambda expressions** (dot notation).

**Important compatibility correction:** SPL2 is **not** an incompatible replacement for SPL. The "Why use SPL2?" page states SPL2 "is **fully compatible** and can operate in parallel with SPL," supports the most popular SPL commands plus **all** statistical and eval functions, lets you embed SPL within SPL2, and provides a point-and-click **SPL→SPL2 converter**.[^whyspl2][^spl2blog] The real constraint: **Edge Processor and Ingest Processor support only a *subset* of SPL2** (e.g., the SPL2 `tstats` does not support `summariesonly`).[^whyspl2][^edge] Treat all SPL2 specifics as volatile and re-verify against current docs.
