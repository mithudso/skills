# Crash-Fault-Tolerant (CFT) Consensus

The CFT family solves consensus / state-machine replication under the **crash (fail-stop) failure model**: a node is either correct or fully stopped — it never sends incorrect or conflicting messages (the non-Byzantine assumption). The unifying bound is **2f+1 replicas to tolerate f crash failures**, progress on any **majority quorum of f+1**; quorum intersection (any two majorities share ≥1 node) carries a committed decision across leader/primary changes. This contrasts with the Byzantine 3f+1 bound (see `byzantine-gossip-crdt.md`). Confidence: **[fact]** = 3+ sources; **[qualified]** = 2.

## Paxos (single-decree synod)

Paxos (Lamport, "The Part-Time Parliament" 1998; "Paxos Made Simple" 2001) splits processes into three roles — **proposers**, **acceptors**, **learners** — and runs in **two phases**.[^simple][^parliament] **Phase 1 (Prepare/Promise):** a proposer picks a globally-unique, monotonically-increasing **proposal number n** and sends `Prepare(n)` to a majority; each acceptor, if it hasn't promised a number ≥ n, *promises* to ignore lower numbers and returns the highest-numbered proposal it has already accepted.[^simple] **Phase 2 (Accept/Accepted):** the proposer sends `Accept(n, v)` where v is its own value **only if no acceptor reported a prior accept — otherwise it must reuse the value of the highest-numbered prior accept**; once a majority accept (n,v), v is **chosen**.[^simple] Safety rests on **majority-quorum intersection**: any two majorities share an acceptor, so a once-chosen value is observed by the next proposer's Phase-1 quorum and propagates forward.[^simple] The kernel is the **single-decree synod** (Lamport's parable of a parliament choosing one decree).[^parliament] Paxos guarantees **safety unconditionally but not liveness** — dueling proposers can livelock; by FLP, terminating election needs randomness or timeouts, so a single **distinguished proposer** must be elected for progress.[^simple] **[fact]**

## Multi-Paxos

SMR needs a *sequence* of values, one per **log slot**; running independent Paxos per slot costs two phases (~4 message delays) each.[^simple] **Multi-Paxos** elects a **stable leader** that runs **Phase 1 once for a whole range of slots**; in steady state clients send commands to the leader, which **skips Phase 1 and runs only Phase 2 (`Accept`) per new slot**, cutting the failure-free delay to ~2 message delays.[^multipaxos] A new leader must run a **full Phase 1 for its first round** to inherit any value a prior leader left behind before switching to the optimized path.[^multipaxos] Production systems add **leader leases**: a time-bounded lease lets the leader serve **linearizable reads locally without a consensus round** because no other leader exists in the lease window (Spanner, CockroachDB).[^leases] **[fact for skip-Phase-1; qualified for lease specifics, which vary by system]**

## Raft

Raft (Ongaro & Ousterhout, "In Search of an Understandable Consensus Algorithm," USENIX ATC 2014) produces a result **equivalent to Multi-Paxos and is as efficient**, but was designed to be **more understandable** by decomposing consensus into **leader election, log replication, and safety**.[^raft] **Leader election:** time is divided into **terms** (monotonic integers acting as logical clocks); a follower that times out becomes a candidate, increments its term, and sends **RequestVote** RPCs; each server grants **at most one vote per term** (persisted), so **Election Safety** holds (≤1 leader per term); split votes break via **randomized election timeouts** in [T, 2T].[^raft] **Log replication:** the leader replicates each command via **AppendEntries** (also heartbeats); an entry is **committed** once on a majority (tracked by the commit index); the prevLogIndex/prevLogTerm check enforces the **Log Matching Property** — *if two logs hold an entry with the same index and term, the logs are identical up through that index*.[^raft] **Safety** rests on the **election restriction** (a candidate's log must be at least as up-to-date as a voter's to win) plus **Leader Completeness** (a committed entry appears in all higher-term leaders' logs), yielding **State Machine Safety** (no two servers apply different entries at the same index); Raft commits previous-term entries only indirectly (by also committing a current-term entry on a majority).[^raft] **Membership changes:** the paper uses **joint consensus** (overlapping old+new majorities); the dissertation prefers **single-server-at-a-time** changes.[^raftdiss] **Log compaction** uses **snapshots**.[^raftdiss] **[fact]**

## Viewstamped Replication

VR was invented by Oki & Liskov (PODC 1988) independently of and contemporaneously with Paxos, **without knowledge of that work**.[^vr1988][^vr2bft] Liskov & Cowling's **VR Revisited** (MIT-CSAIL-TR-2012-021) frames it as a **replication protocol that uses Paxos-like consensus internally**, notably requiring **no disk I/O** on the normal path (persistence comes from replication).[^vrrev] A **primary** orders client requests; **backups** accept that order; the system moves through **views**, each with one primary, and a **view-change** protocol selects a new primary when backups stop hearing from the current one.[^vrrev] It uses **2f+1 replicas, quorums of f+1**, and three sub-protocols: **normal-case, view-change, recovery**.[^vrrev] Normal operation: the primary sends **PREPARE**, waits for **f PREPAREOK** replies (f+1 incl. itself) before committing and up-calling the service, then piggybacks the commit (or sends **COMMIT** when idle).[^vrrev] The "viewstamp" (view-number + op-number) detects lost information across a view change.[^vr1988][^vrrev] VR Revisited also adds reconfiguration that can change group size and f.[^vrrev] **[fact]**

## ZooKeeper / Zab

**Zab** (ZooKeeper Atomic Broadcast; Junqueira, Reed, Serafini, DSN 2011) is a **crash-recovery atomic broadcast** protocol for **primary-backup** systems, leader-based and "similar to Paxos."[^zab][^zkinternals] Its distinctive guarantee is **primary order** (stronger than causal): **local primary order** (FIFO for a single primary) and **global primary order** (state changes from an earlier primary epoch are delivered before a later one's), letting ZooKeeper safely have **multiple outstanding transactions committed in FIFO order** — which Zab's authors note Paxos does not enable directly.[^zab][^zkinternals] Transactions carry a **zxid**, a 64-bit (epoch, counter): the high 32 bits are the **epoch** (incremented per leadership change, guaranteeing a unique proposer per epoch), the low 32 bits a per-proposal counter.[^zkinternals] Zab differs from Paxos by **recovering whole histories** (not single instances), enforcing **prefix/FIFO order** for multiple in-flight ops, and doing **leader-activation processing** that uses epochs to skip blocks of uncommitted proposals.[^zkinternals] It relies on **point-to-point FIFO channels (TCP)** — "if we do not maintain strict FIFO ordering of all packets, it all falls apart" — and uses timeouts for **liveness, not correctness** (FLP-consistent). Recovery uses **DIFF / TRUNC / SNAP** to reconcile a follower's log.[^zkinternals] **[fact]**

## How they relate

All four are **leader/primary-based** SMR solutions sharing the same skeleton: a single leader appends operations to a **replicated log**, replicates to a **majority/quorum (f+1 of 2f+1)**, commits on majority ack, and installs a new leader via a quorum so committed operations survive.[^vrrev][^vivela] Van Renesse et al. ("Vive La Différence") derive Paxos, VR, and Zab from common abstractions, observing **Paxos uses active replication while VR and Zab use passive replication** (primary executes, ships state changes); compute-heavy services favor passive, low-latency short ops favor active.[^vivela] Howard & Mortier ("Paxos vs Raft," 2020) show a Multi-Paxos described in Raft's terms and Raft **"differ only in their approach to leader election"**: **Raft permits only a server with an up-to-date log to become leader** (no log entries exchanged during election), whereas **Paxos lets any server become leader then brings its log up to date** (exchanging entries in RequestVote responses); both prove the same State Machine Safety via the same Leader-Completeness induction over majority intersection.[^paxosvsraft] Lineage: VR → PBFT; Zab → ZooKeeper; Raft now dominates new implementations (etcd, Consul, CockroachDB) while Paxos/Multi-Paxos underlies Chubby/Spanner.[^paxosvsraft] **[fact for shared skeleton + "differ only in leader election"; qualified for active-vs-passive, which the comparison paper says is implementable either way]**

## Disconfirming findings

- **"Raft is more understandable than Paxos" is contested.** Howard & Mortier (Cambridge, 2020) find **no significant difference in understandability** and attribute much of Raft's reputation to the **paper's presentation** rather than the algorithm; the two "differ only in their approach to leader election."[^paxosvsraft] "Raft Refloated" (Cambridge, 2015) confirms Raft's high-level ideas are easier to grasp but warns it "still has many subtleties, particularly regarding the handling of client requests."[^raftrefloated]
- **Raft has had real correctness bugs.** Ongaro's dissertation acknowledges a safety bug (Mazières) and a liveness bug in membership changes (Hoch).[^raftdiss] A **2015 bug in the single-server membership-change algorithm** lets two concurrent cross-term changes have **non-overlapping quorums → split-brain**; the fix requires the leader to commit a current-term entry before appending a new config (the older joint-consensus protocol is unaffected).[^raftbug]
- **Raft does not guarantee liveness under network faults** in basic form: a partitioned server can repeatedly increment its term and disrupt a healthy leader. Fixes — **PreVote** (trial election before incrementing term) and **CheckQuorum** (leader steps down if it loses majority contact) — are in the thesis, not the core ATC paper.[^raftdiss]
- **Zab's published protocol vs ZooKeeper's implementation diverge.** The paper requires atomically persisting history + currentEpoch during sync; ZooKeeper does this asynchronously, so a crash between updating currentEpoch and fsyncing txns can let a stale node win election and **TRUNC away committed transactions** (ZOOKEEPER-4643/4646/4785) — a concrete "theory ≠ reality" gap.[^zkjira]
- **Multi-Paxos is famously underspecified** — Lamport sketched it in a few sentences, yielding divergent, mutually-incompatible production implementations; this (not the core idea) is a recurring complaint and part of Raft's motivation.[^raftrefloated]
